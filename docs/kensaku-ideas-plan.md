# Идеи из kensaku для DigUp Plus: агентный доступ, надёжность, свежесть

**Дата:** 2026-11-04. **Статус:** план к исполнению (0.1.7–0.1.9). Источник — репозиторий
[kensaku](https://github.com/yjid/kensaku) (MIT, Rust/Tauri, Windows-first), локальный клон для разбора:
`C:\Users\sucot\AppData\Local\Temp\kensaku`, коммит `17d5fa2` (2026-11-04). Читал `README.md`,
`docs/ARCHITECTURE.md`, `docs/BENCHMARKS.md`, `Cargo.toml` и код: `agent/mcp.rs`, `agent/mod.rs`,
`agent/connect.rs`, `indexer/extract/external.rs`, `indexer/watcher.rs`, `indexer/walker.rs`,
`indexer/metadata_db.rs`, `search/mod.rs`. Ниже — только то, что проверено по их коду, и что это значит для
нас. Их цифры на 1M файлов в `BENCHMARKS.md` частично экстраполированы — это помечено у них самих.

Код на Rust, копировать нечего; берём решения. Наш козырь (мультимодальные эмбеддинги, файловые операции,
code-индекс, правила папок) не трогаем.

## 1. Агентный доступ (MCP), read-only — главное

**У них** (`agent/mcp.rs`, `agent/mod.rs`, `agent/connect.rs`, `docs/ARCHITECTURE.md` §9.3):

- stdio, newline-delimited JSON-RPC 2.0; stdout — только протокол, диагностика в stderr; `initialize` отвечает
  даже без индекса, инструменты возвращают понятную ошибку (`mcp.rs:40-103`).
- Инструменты: `health_check`, `search`, `read_snippet`, `index_state`, `regex_search`, `find_symbol`
  (tree-sitter), `reindex` — **единственный пишущий, только при `mcp_allow_reindex` и живом демоне**
  (`mcp.rs:185-380,423-466`).
- Бюджеты: `page_size` 10 по умолчанию, максимум 50; сниппет 100 символов; на весь ответ поиска
  `SEARCH_TOKEN_BUDGET = 1500` токенов (≈6000 символов), дальше сниппеты отбрасываются с `truncated`
  (`mcp.rs:30-37,621-651`); `read_snippet` — `max_tokens` 32..1024, «около 4 символов на токен», всегда окно,
  никогда файл целиком (`mcp.rs:780-838`).
- **Ranked vs exhaustive** — разные режимы (`mcp.rs:885-893`): человеку релевантность, агенту полнота с
  `total`/`next_cursor`. Смещение ограничено 10 000 (`MAX_OFFSET`); дальше переключаются на keyset-курсор
  `k2-<hex пути>` (`mcp.rs:32-35,653-667,926-949`).
- **Ограничение области агента**: `agent_scoped_roots` — запрошенный путь пересекается с корнями, чужой путь
  отвергается с ошибкой (`agent/mod.rs:531-631`); пути сравниваются после нормализации.
- Ошибки инструмента: невалидные параметры — JSON-RPC `-32602`, сбой чтения — `isError: true` с текстом
  (`mcp.rs:440-467`). Курсор несовместим с режимом — ошибка, а не тихий перезапуск (`mcp.rs:565-573`).
- `connect.rs`: готовые конфиги для Claude Desktop/Code и Cursor; установка — **merge** в чужой конфиг с
  `.bak`, никогда не перезапись; есть `--print`.

**У нас:** MCP нет вовсе (`digup` знает `search/index/status/estimate/...`, `Sources/digup/main.swift`).
Индекс открывается read-only одной командой `digup search --json`, `Searcher.text(ofSegment:)` уже отдаёт
текст сегмента (`Sources/DigUpKit/Searcher.swift:487`), у сегментов есть `loc` (страница PDF, секунда видео) —
то есть сниппет с местом у нас дешевле, чем у них.

**Решение: `digup mcp` — отдельный MCP-сервер, read-only, поверх локального индекса.**

- Транспорт: stdio JSON-RPC 2.0, версия протокола `2024-11-05`; stdout — протокол, логи в stderr.
  Без shell, без записи; `initialize` работает и без индекса.
- Инструменты v1:
  - `search(query, kinds?, limit≤50, offset/cursor, meaning=true, code=false)` → `path`, `score`, `kind`,
    `size`, `modified`, `snippet` (≤100 символов из `excerpt`/сегмента), `loc?`, `total`, `next_cursor`, `as_of`.
  - `read_snippet(path, segment_id?, query?, max_tokens 32..1024)` → текст сегмента/окна (страница PDF, кусок
    документа, кусок кода), `loc`, `truncated`. Никогда не файл целиком.
  - `index_state()` → файлы по видам, pending/unfinished, модель, возраст индекса (`as_of`), корни.
  - `search` с `code: true` — по `code.sqlite` (у нас он отдельный; у них `find_symbol`, у нас пока нет).
- Ranked/exhaustive: v1 — ranked с `offset` ≤ 10 000 и `next_offset` (у нас пагинация уже есть,
  `docs/search-results-pagination-plan.md`); exhaustive с keyset-курсором — отдельным PR, если агентам
  понадобится больше 10k (иначе честно писать `cursor_limit_reached`).
- Скоуп: настройка `agentScopedRoots` (по умолчанию — выбранные папки); запрос `path` обязан лежать внутри,
  иначе ошибка `path is outside the configured agent scope`; сравнение после нормализации (Windows без
  регистра, junction/symlink раскрывать). Запись, move/copy/delete — недоступны by design.
- Бюджеты: `SEARCH_TOKEN_BUDGET = 1500`, сниппет 100 символов, `read_snippet` 32..1024 токена
  (≈4 символа/токен) — как у них, это уже проверенные числа.
- Конфиги: команда `digup mcp --print-config claude-desktop|claude-code|cursor` печатает JSON; в Settings —
  секция «Agents» с кнопкой «Copy config». Файлы чужих приложений в v1 **не правим** (в отличие от их merge с
  `.bak`): меньше прав и сюрпризов; можно добавить позже.
- Где живёт: процесс долгоживущий (один на сессию агента), открывает `IndexStore`+`Searcher` один раз; модель
  поднимает лениво и только для meaning-запроса; без модели — keyword, как `digup search` сейчас.

**Тесты:** `initialize`/`tools/list`/`tools/call`; неизвестный метод; невалидные параметры (`-32602`);
`page_size` 0/51; курсор вне лимита; путь вне скоупа; отсутствие индекса; бюджет сниппетов; отсутствие
пишущих инструментов (grep по `tools/list`); стабильность `as_of`.

**Сделано (0.1.9):** `digup mcp` (`Sources/DigUpKit/MCP.swift` + `Sources/digup/MCPService.swift`), три инструмента,
бюджеты и скоуп как выше; `--print-config` для Claude Desktop, Claude Code и Cursor; Settings → Storage → Agents с
кнопкой «Copy MCP Config» (шеллинг подставляет свои helper/index/папки/`env`). Отступления от плана: вместо настройки
`agentScopedRoots` — `--root` (по умолчанию весь индекс, но читаются только строки индекса) и Settings передаёт
выбранные папки сама; `as_of` — время последней записи индекса (максимум из `index.sqlite` и `-wal`), а не отдельная
таблица. Инструмента `health_check` нет: `initialize` и `index_state` отвечают и без индекса, чего агенту довольно.
Тесты — `MCPTests` (6): протокол, лимиты, бюджет 6000 символов с `next_offset` по отданным строкам, окно
`read_snippet`, скоуп, отсутствие индекса; живой прогон на dev-индексе и на индексe кода. Документ для человека:
`docs/agent-access.md`.

**Оценка:** 1,5–2 дня. Риск средний (новый протокол), но изолирован: индекс только читается.

## 2. Надёжность инкремента: что у нас уже есть и чего не хватает

Проверено по нашему коду, чтобы не чинить несуществующее:

- **Overflow уже обрабатывается**: пустое событие watcher'а означает «система потеряла события», бурст
  очищается, и `sync_paths` с пустым списком зовёт полный `run` (`shell/src-tauri/src/watcher.rs:43-51,69,87-92`;
  `helper.rs:301-309`). Это ровно их `need_rescan` → полный rescan.
- **Чего нет:**
  1. **Кулдаун на повторные overflow.** У них `RESCAN_COOLDOWN = 60 s` и один rescan в полёте
     (`watcher.rs:49-56,360-412`); у нас каждый overflow — новый полный синк (спасает только `yieldAt` в
     helper'е). Добавить: не чаще одного overflow-синка в 60 с, остальные схлопывать.
  2. **Проверка «файл ещё пишется».** У них `SETTLE = 400 ms`, затем повтор через `FRESH_RETRY = 500 ms`, пока
     `(size, mtime)` не стабилизируются, окно `FRESH_WINDOW = 10 s` (`watcher.rs:49-58,116-160`). У нас бурст 2 с,
     но без повторной проверки: недописанный PDF/видео может попасть в индекс как «failed», хотя через секунду
     стал целым. Добавить в watcher: держать `(size, mtime)` и пересеривать.
  3. **Фолбэк, когда watch не работает.** У нас ошибка `watch` только в stderr, watcher остаётся пустым
     (`watcher.rs:55-64`), статус об этом не знает. Добавить флаг в статус («changes aren't being watched») и
     периодический полный синк (5 мин) вместо тихой потери изменений на сетевых/exFAT дисках.
  4. **Мусор до любой работы.** У них отдельного junk-списка в коде нет (это только в
     `ARCHITECTURE.md`), но у нас нет и `~$*.docx`: офисный lock-файл (~162 байта, не hidden) классифицируется
     как документ и читается/падает. Добавить в `Rules`/`Crawler`: `~$*`, `*.tmp`, `.swp/.swo`, `4913`,
     `.git/index.lock`, `*.crdownload`, `desktop.ini`, `Thumbs.db` (последние два — по имени).
- **Repair-проход 1 % у них описан, но в коде его нет** (грепал `repair` — только миграция конфига). И нам он
  не нужен: наш синк и так статит каждый файл; добавить нечего. **Отвергнуто** (см. §8).

**Оценка:** кулдаун 1 ч, fresh-retry 2–3 ч, фолбэк+статус 3–4 ч, мусор 1 ч. Тесты: overflow-шторм → один синк;
файл дописывается → читается один раз, но целым; watcher не стартовал → статус и периодический синк; `~$x.docx`
не в индексе.

## 3. Свежесть как число

**У них:** каждый ответ (GUI, CLI, MCP) несёт `as_of`; в подвале окна `12 ms · 1.2M files · 2 s old ·
semantic ✓`; `last_reconcile` в состоянии (`commands.rs:368,434`; `agent/mcp.rs:679,864`). «Search-first,
reconcile-after» у них — загрузка снапшота и фоновая сверка; у нас это уже есть по архитектуре (search-service
читает индекс независимо от индексатора), не хватает только **видимого возраста**.

**Решение:** в `status.rs` хранить время последнего `sync` (в событии уже есть `started`,
`IndexService.swift:260`); отдавать `indexAgeSeconds` и `asOf` в `settings_info`/`window_info`/`panel`-состоянии
и в MCP `search`/`index_state`; в окне/панели — строка «index 2 min old» рядом со статусом, в Settings —
«last sync 2 min ago». Дёшево (2–3 ч) и снимает вопрос «вижу ли я свежие файлы».

## 4. Frecency (ранжирование по тому, что человек открывает)

**У них:** таблица `usage(path, opens, last_open)` (`metadata_db.rs:80-90,484-514`), бонус
`+0.08 · ln(1+opens) · exp(-days/14)` в ранжировании (`search/mod.rs:1619-1623`). Локально, без сети.

**У нас:** учёта открытий нет. **Решение (отдельный PR, только с evals до/после):**

- Хранилище — **отдельная** `usage.sqlite` в папке данных (не в индексе: reindex его не должен стирать).
- Шелл при `open_path`/`open_code` (и «Reveal») шлёт поисковому helper'у `{"op":"used","path":…,"code":false}`;
  helper делает upsert (opens+1, last_open=now).
- Ранжирование: бонус добавляется к fused-score **после** слияния и **только** в обычном ranked-режиме; в
  `by_cosine`-слоях Images не применяется (там ранг — это cosine, бонус сломал бы слои).
- Настройка «Remember what I open» (по умолчанию вкл.) + «Clear» в Settings; локально, никогда не уходит.
- Открытие по пути: переименование теряет историю — приемлемо (у них так же; при желании ключ `(device, inode)`
  как в индексе).
- Проверка: `digup eval evals/*.json` до/после на дефолтах; вес 0.08 — стартовая точка, подбирать только с
  числами.

**Оценка:** 6–8 ч с evals. Риск: меняет выдачу — без eval не включать.

## 5. Внешние экстракторы (наш отложенный этап «плагины»)

**У них** (`indexer/extract/external.rs`, `docs/EXTRACTORS.md`): `ExternalExtractor { name, extensions, mime,
command, args, timeout_ms 100..7000, max_output_bytes ≤4 MiB, enabled }`.

- `validate`: непустое имя, хотя бы один селектор, ≤128 аргументов, команда — **абсолютный существующий файл**;
  на Windows `.bat/.cmd` отвергаются (Rust иначе прогнал бы их через cmd.exe) — гарантия «без shell»
  (`external.rs:384-431`).
- `run`: `env_clear` + минимум (`PATH`, на Windows ещё `SYSTEMROOT/WINDIR/TEMP/TMP`), cwd = папка файла, stdin
  null, stdout с потолком, stderr null, таймаут, **kill всей process group** (Unix), `{path}` как один аргумент,
  по умолчанию реестр пуст, ошибки видны в Doctor (`external.rs:168-330`).

**Для нас:** это контракт для фазы 4 (`docs/per-folder-rules-plan.md`), а не для 0.1.7. Записать в план фазы 4:
абсолютный exe, без `.bat/.cmd`, очищенное окружение, cwd файла, таймаут, kill группы, потолок вывода,
выключено по умолчанию, ошибки в статусе/Doctor, никакого shell. Отличие: наш экстрактор отдаёт не только
текст, но и сегменты (текст/вектор) — спецификация JSON-lines на вход/выход, и предупреждение в UI, что внешний
код может делать что угодно (сеть в том числе) — песочницы нет, только доверие пользователя.

## 6. UX-инварианты (документ + проверки, не код)

Их список (`ARCHITECTURE.md` §1) стоит взять как чек-лист для окна/панели: набор не блокируется; никогда
«blank → spinner» (старые результаты остаются); порядок не меняется, пока печатают; свежесть видна;
фильтры видимы (невидимый фильтр — баг); чипы и один поиск. У нас большая часть есть (keyword-сначала,
предыдущие результаты, чипы, `code:`), но не сформулирована — добавить в `docs/development-guide.md`
(2–3 ч) и проверить, что «индекс старый» теперь видим (§3).

## 7. Что отвергнуто (с причинами)

- **Статические эмбеддинги (model2vec, 7.7 МБ, ~50 µs/запрос)** — второй векторный мир; у нас смысл в
  мультимодальном качестве. Только как «режим без модели» — отдельный продукт.
- **RRF вместо наших весов/z-гейта** — наши веса измерены; RRF можно один раз прогнать на evals, но не менять
  вслепую.
- **Query-грамматика с чипами** (`type:`, `in:`, `modified:`) — полезно, но не срочно; у нас есть `code:` и
  фильтры.
- **Facets по всему результату** — у нас есть counts по видам; facets по дате/размеру — средняя работа.
- **ANN/HNSW, USN-журнал, daemon-split** — у нас другой масштаб/архитектура (helper'ы уже есть).
- **Repair-проход 1 %** — наш синк и так статит каждый файл; дублировать нечего.
- **Пишущие MCP-инструменты (reindex)** — read-only проще и безопаснее; reindex есть в UI.
- **Автоматическая правка чужих конфигов агентов** — только печать/копирование в v1.

**Сделано (0.1.8)** — по пунктам §2 и §3:

- **Кулдаун overflow:** `watcher.rs`, `OVERFLOW_COOLDOWN = 60 с`: второй «система потеряла события» ждёт, пока
  первому не исполнится минута (спит в потоке watcher'а; накопленные за это время пути всё равно придут следующим
  бурстом). Тест: `overflow_syncs_wait_a_minute`.
- **Fresh-retry:** `settle` перед `changed`: (size, mtime) всех файлов бурста, повтор через 500 мс, окно 10 с; папки и
  пропавшие файлы не ждут. Тест: `a_writing_file_is_seen_changing` (файл дописывается → снимки различаются; папка и
  отсутствующий файл — `None`).
- **Фолбэк + статус:** `FolderWatcher::start` помнит папки, которые `notify` не взял (или бэкенд не создался), и раз в
  5 минут шлёт их как обычный бурст (scoped-синк этих папок; поток гаснет на `Drop` через атомарный флаг, шагами по
  1 с). `FolderWatcher::watching()` → `Status.watching`; строка статуса получает «· changes aren't watched» (тест
  статуса), в снапшоте — `watching`.
- **Мусор:** `Rules.isJunk` (`~$*`, `*.tmp`, `.swp/.swo`, `4913`, `*.crdownload`, `desktop.ini`, `Thumbs.db`) и проверка
  в `Crawler.visit` до классификации (причина «a program's leftover» в `leftOut`); тот же список в `watcher.rs`
  (`is_junk`), чтобы правка Word'ом открытого документа не звала синк. Тест: `programLeftoversAreNotRead`. Живая
  проверка: папка с `~$lock.wav` и `Thumbs.db` → оба в `left_out`, `Keep Me.wav` проиндексирован.
- **Свежесть:** `Status.last_sync` из `started` события `sync`; `asOf` в снапшоте (окно/панель/настройки); в окне —
  «3 files indexed · synced just now» (перерисовка раз в 30 с), в Settings — «last sync 2 min ago» в строке деталей.
  Живая проверка формата: «just now» / «2 min ago» / «3 h ago».

Сознательно не сделано: строка возраста в панели (место занято числом результатов и caveat; окно и Settings его
показывают), и «repair»-проход (синк и так статит каждый файл).

## 8. Порядок и релизы

1. **0.1.7** — уже запланированное в `docs/per-folder-rules-plan.md` (аудио двумя битами, теги в UI, оценка с
   правилами). MCP не смешивать.
2. **0.1.8** — надёжность и свежесть: кулдаун overflow, fresh-retry, фолбэк-синк + видимый статус, junk-фильтр,
   `indexAge`/`asOf` в статусе, строка «index N old»; плюс **Rescan и Re-read одной папки**
   (`docs/per-folder-rules-plan.md`, «После 0.1.7»). Риск низкий, всё внутри shell/краулера.
3. **0.1.9** — MCP read-only (`digup mcp`, 3 инструмента, скоуп, бюджеты, `--print-config`). Отдельный релиз:
   новая поверхность, нужна обкатка на Claude/Cursor.
4. **Frecency** — после MCP, только с evals до/после и настройкой «забыть историю».
5. **Фаза 4 (плагины)** — когда дойдёт очередь; контракт из §5 в план.

**Общие риски:** MCP — утечка лишнего через сниппеты (ограничить бюджетом и `max_tokens`, не отдавать файл
целиком), скоуп на Windows (junction/symlink — нормализовать, иначе обход), frecency меняет ранжирование
(только с evals), fresh-retry может зациклиться на файле, который постоянно дописывается (жёсткий потолок 10 с,
потом обычная обработка).

## 9. Что проверено по коду, а что — только по их документам
