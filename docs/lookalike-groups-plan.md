# Look-alike groups in Find similar

Состояние: **план согласован с владельцем 2026-11-12, внедрение не начато.** Границы, поведение и настройки
согласованы; ниже — конкретные решения, проверка последствий по коду и замерам, и порядок работ.

## 1. Цель и что не входит

В режиме **Find similar** («похожие» из контекстного меню) выдача уже подобрана по смыслу, но визуально близкие
кадры — серии, варианты, кадры подряд, полные копии — стоят отдельными ячейками. Второй проход группирует **уже
найденное**, не меняя ранжирование: группа сворачивается в одну ячейку с бейджем «+N».

Не входит:

- обычный поиск (по смыслу, по словам) — не меняется вообще;
- видео, аудио, документы, код — только изображения и скриншоты;
- таблица (там сортировка по колонкам) — плоский список;
- маленькая панель — в ней нет «Find similar»;
- никаких удалений/переименований/пометок файлов: перемещение и удаление делает сам человек, как сейчас.

## 2. Решения

- **Триггер**: режим «Find similar» и результаты — изображения/скриншоты. Эталон — файл, от которого ищут.
- **Группировка на месте**: представитель — лучший по косинусу к эталону; остальные члены убраны под бейдж.
  Клик — развернуть/свернуть; состояние живёт до нового запроса. Догрузка страниц вливает новых членов в
  существующие группы (раскрытая группа остаётся раскрытой).
- **Выделение**: свёрнутая ячейка = только представитель. Видимые строки — то, что можно выбрать (Ctrl+A, клики,
  «Selected to TC», файловые операции). Скрытые члены не выбираются никогда.
- **Настройки**: `lookalikeGroups` (bool, по умолчанию **вкл**), `lookalikeDifference` (%, по умолчанию **6**,
  диапазон 0–50). Живой регулятор — строка под чипами только в этом режиме: `12 groups · 41 folded · difference 6%`,
  число открывает поповер (галочка, поле, «Reset 6%», счётчик «41 из 120»). Та же цифра — в Settings → Search.
  Смена значения пересчитывает группы мгновенно; индексация не затрагивается.
- **Сообщения**: выше ~20% — тихая подпись, что в группы попадают разные кадры.

## 3. Движок: pHash-256

Рецепт (из AntiDuplPlus, MIT, с упоминанием в notices): серый кадр → 64×64 (bilinear) → DCT-II по осям → блок
`[0:16, 0:16]` → медиана 256 коэффициентов → бит = `коэффициент > медианы`. Различие пары — `100 × hamming / 256`
(как «difference» в AntiDuplPlus). Варианты D4 (повороты/зеркала) в первой версии не берём: в целевых сценариях
(серии, пережатые копии, скриншоты) хватает одной ориентации; добавляются позже ещё 224 байта на строку.

## 4. Что проверено (до внесения изменений)

Замеры на реальном индексе владельца (4259 изображений, `.build/real-index`, чтение), 2026-11-12:

- **Стабильность хеша** (8 случайных фото × варианты; отличие в % от исходного):

  | вариант | отличие |
  |---|---|
  | resize 50/25/12% + JPEG q80–90 | 0–1.6% |
  | повторный JPEG q60 / q40 при том же размере | 0–0.8% |
  | grayscale | 0% |
  | яркость +10% | 0.8–3.9% |
  | кроп 5% по краям | **25–40%** |

  То есть порог 6% накрывает пережатие/ресайз/яркость с запасом и не склеивает кропы; 33% (умолчание AntiDuplPlus)
  склеивает и кропы — это осознанно остаётся верхней частью диапазона.

- **Группировка на 120 векторных соседях** (3 разных сида): AI-серия — 10 групп, 42 из 120, крупнейшая 21 вариант
  (SSIM 0.96–1.0); превью YouTube — одна группа, и это настоящая копия (файлы побайтово равны); фото-сид — 0–1
  группа. Ложных склеек на этих данных не было (в отличие от 64-битного dHash из SpaceLens, который склеил
  «женщина на белом» ↔ «бутылка шампанского»).

- **Стоимость**: 120 картинок — 1.65 с с чтением и декодом (Python; в движке хеш считается один раз при индексации),
  поиск пар 45k — 0.05 с. С сохранёнными хешами группировка запроса — единицы миллисекунд.

- **Код (последствия проверены чтением, не догадками)**:
  - схема индекса версионируется `PRAGMA user_version` (сейчас 6), миграции — по одной в транзакции
    (`IndexStore.migrate`), колонка добавляется с проверкой наличия (`migrateTagsOnly` — образец);
  - образец «досчёта без переиндексации» уже есть: `Indexer.backfillTagFields` + `meta`-ключ;
  - пакетная индексация картинок: `ImageExtractor.prepare` пишет уменьшенную копию (портативная ветка —
    `Platform/Portable/Images+Portable.swift`, `RGBImage` с `averageHash()` — 64-битный aHash уже есть, но это другой
    хеш и в индексе он не хранится);
  - выдача: `SearchService` собирает хит из `hitFields`; ранжирование, `total`, `next_offset`, `generation`,
    `kind_totals`, `tier_counts` не затрагиваются;
  - окно: `rows()` — единственная точка «что видно» (выделение, Ctrl+A, экспорт, операции, клавиатура);
    `state.ranked/weaker/hidden` остаются полным рейтингом; после операций уже есть пересборка (`applyOperation`
    фильтрует ушедшие пути) — группы чистятся в том же месте;
  - настройки: `set_search_settings` — образец сохранения пары значений в `settings.json` с событием для окна.

## 5. Последствия по подсистемам

| Подсистема | Что меняется | Как проверяется |
|---|---|---|
| Схема индекса | v7: `files.phash BLOB` (32 байта), `meta('phash_recipe') = phash256-dct16-v1` | тест миграции с фикстурой v6; повторное открытие |
| Индексация | pHash из подготовленной копии после декода; только `image`/`screenshot`; +1–3 мс на файл | тест: хеш готов после `prepare`; NULL у остальных |
| Старый индекс | группировка ждёт досчёта; первый запрос досчитывает только показанные хиты и сохраняет их (≈1.7 с один раз), фоном — очередь; CLI `digup phash` для разового прогона | живой прогон на копии индекса владельца |
| Смена рецепта | несовпадение `phash_recipe` обнуляет колонку (без переиндексации векторов) | тест |
| Выдача | новый op `visual_groups` (пути + difference → группы); `hitFields` и CLI-выдача не меняются | юнит-тест группировки, контракт op |
| Пагинация | не меняется: группы — представление уже загруженного | живой прогон: «Show more», счётчики |
| Таблица | группировка выключена | ручная проверка |
| Выделение | `rows()` отдаёт только видимые; скрытые члены недоступны для выбора; `state.selection` переезжает на представителя; скрытые пути убираются из `state.selected` | тесты сценариев + CDP |
| Move/Delete | группы чистятся после операции; группа из одного члена распадается | CDP: удалить члена, проверить выдачу |
| Total Commander | `Selected to TC` — видимые; `All to TC` — весь рейтинг, как сейчас | ручная проверка |
| MCP, панель | не затрагиваются (op не вызывают) | отсутствие изменений в их протоколе |
| Evals | ранжирование не меняется; сравнение «до/после» без включённых групп идентично | `digup eval` до и после на всякий случай |

## 6. Фазы

1. **Движок** (≈1 день): `Phash256` (чистая математика), загрузчик 64×64 для Portable/Apple, поле в схеме v7,
   досчёт, `LookalikeGroups` (union-find), тесты: стабильность (ресайз/качество/яркость/кроп), границы порога,
   миграция v6→v7, идемпотентность досчёта.
2. **Сервис** (≈0.5 дня): op `visual_groups`, досчёт недостающих хешей с сохранением, `digup phash` для прогона;
   проверка на копии реального индекса — цифры групп при 3/6/12% по нескольким сидам.
3. **Окно** (≈1 день): состояние групп, свёртка/разворот, бейдж, строка с процентом и поповером, галочка, счётчик,
   безопасное выделение (`rows()`), чистка после операций, статус; `node --check` + CDP-сценарии.
4. **Настройки и приёмка** (≈0.5 дня): поля в `settings.json`, Settings → Search, событие обновления окна;
   живой прогон на dev-окне; упакованная проверка. Дальше — визуальный тест владельца и подгонка умолчания.

## 7. Риски и ограничения

- Кропы, повороты, зеркала на 6% не склеиваются (D4 — отдельная, более поздняя опция; кроп — только высокие
  значения, с риском лишних склеек).
- EXIF-ориентация должна быть применена до хеша — считается с подготовленной копии, где ориентация уже учтена.
- Коллекции с сериями/AI-генерациями группируются агрессивно: поэтому бейдж обратимый, есть галочка и порог.
- `O(n²)` при 300 загруженных — единицы миллисекунд; для десятков тысяч (не наш случай) понадобится LSH-разбиение,
  как в AntiDuplPlus (полосы/индексы) — заложено как запасной путь, не в первой версии.
- Индекс растёт на 32 байта на изображение (~136 КБ на 4.3 тыс.) — пренебрежимо.
