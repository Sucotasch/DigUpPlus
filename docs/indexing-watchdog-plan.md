# Watchdog и очередь: таймаут (#174) и память/остановки (#182)

План. Собран из обсуждения и замеров, а не из догадок. Числа, помеченные «проверить», пока не приняты: для них
задан способ измерить и правило выбора. Код не меняется, пока план не уточнён спайками (раздел 3).

Контекст: `docs/development-guide.md`, `Sources/digup/Watchdog.swift`, `Sources/DigUpKit/Indexer.swift`,
`Sources/DigUpKit/Platform/Portable/Media+Portable.swift`, `shell/src-tauri/src/main.rs`.

## 1. Проверенные факты

**Таймаут (#174).**

- `Watchdog.defaultTimeLimit = 15 * 60`; отсчёт — от `reading.since`, **начала чтения**; прогресса нет
  (`Watchdog.swift:21,38`).
- `Indexer.nowReading` — самый старый из читаемых файлов (`Indexer.swift:513`); при нескольких чтениях зависшее
  может оказаться не самым старым, и наблюдатель смотрит не на него.
- Видео: **один ffmpeg** на keyframes (декодирует весь клип, пишет JPEG в папку, stdout пуст) и **второй** — на звук
  (s16le в stdout). Звук отдаёт данные кусками по 64 КБ (`Media+Portable.swift:124-142`), keyframes — только файлы
  (`:165-168`).
- Замер вендоренного ffmpeg (`-progress pipe:1`, клип 12 с, `fps=1/5`, `-re`): **блок прогресса каждые ~0.5 с**, даже
  когда новый кадр ещё не вышел (`frame=1`, `out_time=5s` повторяются 5 секунд). То есть «молчание» — признак
  зависания; но `out_time`/`frame` могут законно не двигаться, пока декодируется следующий кадр.
- Остановка: `stopped-file.json` + выход 75; следующий helper помечает файл `failed` (или `partial` → `done` с
  «остальное не прочитано») (`IndexStore.swift:757-767`).
- `failed` не перечитывается, пока файл не изменят; команды «повторить неудачные» нет.
- Оболочка перезапускает helper по 75, но **не более 3 остановок за 10 минут**, дальше «индексирование остановлено»
  (`main.rs:3927-3948`). Падения без заметки (OOM-kill, access violation) не перезапускают.

**Память и очередь (#182).**

- Лимит памяти: macOS — `task_info`, Linux — `statm`, **Windows — `nil`**, то есть на Windows проверки памяти нет
  (`Watchdog.swift:62-79`). Лимит 4–8 ГБ, на процесс.
- Очередь: `screenshot → image → pdf → doc → audio → video → прочее`, затем mtime desc (`Model.swift:10-12`).
- Читается **одно не-картиночное задание за раз**; `prepareAhead` действует только на картинки
  (`Indexer.swift:324-343`). Новые файлы идут **без idle-гейта**; гейт стоит на доборе длинных файлов
  (`IndexService.swift:314-318,344-345`) и делает паузы **между шагами** — у видео шаг один, поэтому idle-режим его
  не замедляет.
- `process` уже перекрывает подготовку следующего задания со встраиванием текущего; колбэк `committed` **игнорирует
  индекс задания**, итоги и события от порядка не зависят (`Indexer.swift:235,302-361`). Значит коммиты вне очереди
  безопасны.
- `--time-limit`/`--memory-limit` у helper'а есть, но оболочка их не передаёт и в интерфейсе их нет
  (`main.swift:35-37,517-519`).

## 2. Предварительные решения

### D1. Таймаут — по прогрессу, фазами

- `Indexer` хранит для каждого чтения `started`, `lastSignal` (был блок), `lastMove` (сдвинулся `out_time`/`frame`/
  страница/чанк). Наблюдатель смотрит **чтение с самым долгим молчанием**, а не самое старое.
- Бюджеты:
  - **старт**: 90 с до первого сигнала (запуск, антивирус, `ffprobe`, раскрутка диска) — «проверить» пункт 3;
  - **живость**: 20 с без любого сигнала; при пониженном приоритете — 40 с, если спайк 1 покажет растяжение блоков;
  - **движение**: 5 мин без роста `out_time`/страницы — предварительно; правило: `max(60 с, 4 × самый долгий интервал
    между сдвигами при 0.2×)`, уточняется спайком 2;
  - **хеширование кадров** после ffmpeg — heartbeat на кадр, порог живости тот же;
  - **общий** 15-минутный лимит для медиа **убрать**: он не нужен, если есть живость и движение;
  - **память** — как есть (плюс D6 для Windows).
- Часы — **без сна**: Windows `QueryUnbiasedInterruptTime`, POSIX `mach_absolute_time`/`CLOCK_MONOTONIC` (иначе сон
  ноутбука «убивает» здоровое видео).
- Сигналы: звук — каждый прочитанный кусок stdout; видео — строки `-progress pipe:1` (`out_time_us`, `frame`);
  документы/PDF — шаг уже отдельный `prepare`; картинки — файл в батче.
- Сообщения остановки: «gave no sign for 90 s» / «made no progress for 20 s» / «frozen at 00:12:30 for 5 minutes».

### D2. Понижать нагрузку длинных чтений

- Понижать приоритет **дочерних** ffmpeg/ffprobe (не helper'а): Windows `SetPriorityClass` (BELOW_NORMAL или
  BACKGROUND_BEGIN), POSIX `setpriority` ребёнку; helper остаётся обычным, иначе на POSIX `nice` не откатить.
- Для аудио/видео — `-threads 1 -filter_threads 1`; при необходимости ограничить и встраивание кадров (потолок бюджета
  кадров).
- Idle-only для медиа **не делать** (согласовано): медиа индексируется всегда, но медленнее.
- Опция (не в первой версии): «видео/аудио: сразу / после коротких / на низком приоритете».

### D3. Очередь и остановки

- Состояние **`deferred`** (TEXT, схема не меняется): остановленный файл попадает туда с временем «попробовать после»
  (backoff: 1 ч, затем 1 день), сортируется **после всех**, берётся, когда основное пусто; `failed` остаётся для
  явных ошибок чтения (не остановок).
- Оболочка: выход 75 перезапускает **всегда** (заметка = прогресс: один файл помечен); ограничение «3 за 10 минут» —
  только для выходов **без** заметки; защита от повторов 75 на одном пути; перезапуск — с низким приоритетом и
  коротким backoff.
- Действие «Попробовать отложенные/неудачные ещё раз» (статус или настройки) + однократный retry после обновления
  версии/лимитов. Без него старые `failed` останутся навсегда.

### D4. «Сильная полоса» для медиа — после спайков

- **4a (дешёво)**: `prepareAhead` для медиа = 1 — следующее задание готовится, пока встраивается текущее; уже почти
  работает, но `fill` для не-картинок держит глубину 1.
- **4b (если 4a мало)**: одно медиа готовится в фоне, основной поток обрабатывает короткие файлы, медиа коммитится
  позже. Коммиты вне очереди безопасны (факт выше). Наблюдатель — по молчанию каждого чтения. Память: один подготовленный
  + один встраиваемый набор кадров; кадры — на диске.
- Решение между 4a и 4b — по спайку 6 (медленное видео + 200 коротких файлов).

### D5. Windows: память

- `Watchdog.footprint()` для Windows через `K32GetProcessMemoryInfo` (`WorkingSetSize` или `PrivateUsage`), те же
  4–8 ГБ. Это превращает OOM-крах без заметки в обычную остановку с заметкой.
- Падения без заметки (AV) остаются неатрибутированными; «хлебная крошка» `reading.json` — отдельным решением позже,
  если после D5 такие падения останутся.

## 3. Проверки до кода (спайки, без изменений продукта)

1. `-progress` под BELOW_NORMAL/IDLE и с `-threads 1` на реальном 4K: остаются ли блоки ~0.5 с (от этого 20 или 40 с).
2. `out_time` на реальном 4K при 0.2–0.3×: самый долгий интервал между сдвигами → правило для 5 мин.
3. `ffprobe` на SMB-шаре и на «спящем» HDD: время до первого сигнала → бюджет «старт» (90 с?).
4. Windows: `GetProcessMemoryInfo` против Task Manager; пик на NEF/TIFF; падает ли helper и с каким кодом.
5. Часы без сна: `QueryUnbiasedInterruptTime` на Windows, `CLOCK_MONOTONIC`/`mach_absolute_time` на Linux/macOS;
   проверить, что сон не считается молчанием.
6. Прототип 4a и 4b: медленное видео + 200 коротких файлов; короткие не ждут; память; счётчики/статусы; наблюдатель
   ловит зависание при двух чтениях.
7. Воспроизвести «3 остановки за 10 минут» на 4 подставных плохих файлах: действительно ли оболочка встаёт.

## 4. Последствия (что затронет)

- **Свежесть медиа**: D4/приоритеты делают медиа позже; нужен promotion («Index Now», опция, возможно фильтр) и
  честная строка в статусе. Без promotion видео может «не находиться» дольше.
- **Состояния/интерфейс**: `deferred` — новый счётчик и строка статуса; окно и `IndexService` знают только
  `pending/done/partial/skipped/failed` — провести через все места.
- **Перезапуски**: 75 всегда → много перезапусков на серии плохих файлов (каждый помечает один); guard только для
  падений без заметки, иначе цикл.
- **Память**: D4b — два медиа в работе; кадры на диске, модель грузит один батч; проверить `frameBudget`.
- **Платформы**: D5 и D2 — разные API на Windows/POSIX; POSIX `nice` не откатывается, поэтому только дети.
- **Схема**: `deferred` — значение в TEXT-поле, миграции нет; но старые индексы должны корректно показывать новое
  состояние (проверить чтение/запись и окно).
- **Тесты**: юнит на бюджеты/часы (подставные часы и сигналы); интеграция `--time-limit`/`--memory-limit` на маленьком
  фикстуре; живой гейт: папка с медленным видео и пачкой коротких файлов, проверка «короткие не ждут» (если 4b),
  статусов, отсутствия temp; существующие гейты (индекс/поиск) не должны измениться.
- **Документация**: `AGENTS.md`/`docs/development-guide.md` — новое поведение; `--time-limit` help; заметка о
  `deferred` для окна.

## 5. Порядок работ

1. Спайки 1–7, цифры в план (ничего не меняем в продукте).
2. Уточнение плана: бюджеты, нужна ли 4b, как показывать `deferred`.
3. D1 (прогресс, фазы, часы) + тесты.
4. D5 (память Windows) + тест.
5. D2 (приоритет детей, `-threads 1`) + замеры.
6. D3 (`deferred`, перезапуски, retry) + тесты.
7. D4a, затем 4b только по результату спайка.
8. Пакет, полный набор гейтов, запись в guide.

Каждый шаг — отдельный коммит; релиз не публикуется, пока не проверено на пакетной паре.

## 6. Чего в этом плане нет

- «Хлебной крошки» для падений без заметки (отдельное решение, риск обвинить не тот файл).
- Idle-only для медиа (отвергнуто: на активной машине медиа не индексировалось бы вовсе).
- Настройки лимитов в интерфейсе (пока только CLI/внутренние значения).
- Изменений в поиске, OCR, схеме индекса, кроме значения `deferred`.
