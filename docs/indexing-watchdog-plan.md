# Watchdog и очередь: таймаут (#174) и память/остановки (#182)

План. Собран из обсуждения и замеров, а не из догадок. Числа, помеченные «проверить», пока не приняты: для них
задан способ измерить и правило выбора. Код не меняется, пока план не уточнён спайками (раздел 3).

Контекст: `docs/development-guide.md`, `Sources/digup/Watchdog.swift`, `Sources/DigUpKit/Indexer.swift`,
`Sources/DigUpKit/Platform/Portable/Media+Portable.swift`, `shell/src-tauri/src/main.rs`.

## 1. Проверенные факты

**Таймаут (#174).**

- `Watchdog.defaultTimeLimit = 15 * 60`; отсчёт — от `reading.since`, **начала чтения**; прогресса нет
  (`Watchdog.swift:21,38`).
- `Indexer.nowReading` — самый старый из читаемых файлов (`Indexer.swift:513`); при нескольких чтениях зависшее
  может оказаться не самым старым, и наблюдатель смотрит не на него.
- Видео: **один ffmpeg** на keyframes (декодирует весь клип, пишет JPEG в папку, stdout пуст) и **второй** — на звук
  (s16le в stdout). Звук отдаёт данные кусками по 64 КБ (`Media+Portable.swift:124-142`), keyframes — только файлы
  (`:165-168`).
- Замер вендоренного ffmpeg (`-progress pipe:1`, клип 12 с, `fps=1/5`, `-re`): **блок прогресса каждые ~0.5 с**, даже
  когда новый кадр ещё не вышел (`frame=1`, `out_time=5s` повторяются 5 секунд). То есть «молчание» — признак
  зависания; но `out_time`/`frame` могут законно не двигаться, пока декодируется следующий кадр.
- Остановка: `stopped-file.json` + выход 75; следующий helper помечает файл `failed` (или `partial` → `done` с
  «остальное не прочитано») (`IndexStore.swift:757-767`).
- `failed` не перечитывается, пока файл не изменят; команды «повторить неудачные» нет.
- Оболочка перезапускает helper по 75, но **не более 3 остановок за 10 минут**, дальше «индексирование остановлено»
  (`main.rs:3927-3948`). Падения без заметки (OOM-kill, access violation) не перезапускают.

**Память и очередь (#182).**

- Лимит памяти: macOS — `task_info`, Linux — `statm`, **Windows — `nil`**, то есть на Windows проверки памяти нет
  (`Watchdog.swift:62-79`). Лимит 4–8 ГБ, на процесс.
- Очередь: `screenshot → image → pdf → doc → audio → video → прочее`, затем mtime desc (`Model.swift:10-12`).
- Читается **одно не-картиночное задание за раз**; `prepareAhead` действует только на картинки
  (`Indexer.swift:324-343`). Новые файлы идут **без idle-гейта**; гейт стоит на доборе длинных файлов
  (`IndexService.swift:314-318,344-345`) и делает паузы **между шагами** — у видео шаг один, поэтому idle-режим его
  не замедляет.
- `process` уже перекрывает подготовку следующего задания со встраиванием текущего; колбэк `committed` **игнорирует
  индекс задания**, итоги и события от порядка не зависят (`Indexer.swift:235,302-361`). Значит коммиты вне очереди
  безопасны.
- `--time-limit`/`--memory-limit` у helper'а есть, но оболочка их не передаёт и в интерфейсе их нет
  (`main.swift:35-37,517-519`).

## 2. Предварительные решения

### D1. Таймаут — по прогрессу, фазами

- `Indexer` хранит для каждого чтения `started`, `lastSignal` (был блок), `lastMove` (сдвинулся `out_time`/`frame`/
  страница/чанк). Наблюдатель смотрит **чтение с самым долгим молчанием**, а не самое старое.
- Бюджеты — **правила от измерений (часть уже проведена, §3.1)**:
  - **старт**: локально `ffprobe` — 47–68 мс; внешний USB HDD (раскручен) — 61–75 мс и первый блок 0.58 с; бюджет
    `max(30 с, 2× худшего)` для локальных и внешних путей. Для UNC — 90 с как **политика** (SMB сейчас недоступен,
    типичные таймауты 30–60 с), уточнить по замеру; спящий диск — оценка 5–15 с, укладывается;
  - **живость**: блок идёт каждые ~0.5 с (замер: 27 блоков за 14.3 с на 4K; 0.5 с и при 0.2×); бюджет 40× = **20 с**
    на нормальном приоритете. На BELOW_NORMAL/IDLE под нагрузкой — **40 с** (замер: 34 блока за 113 с, в среднем
    3.3 с);
  - **движение**: `out_time` идёт по кадрам; замер: шаг 3 с при 0.2× → каждые 15 с; 4K 60 с на одном потоке —
    каждые 0.7 с. Для 1–3 ч при 0.1× это 30–90 с, поэтому порог **90–120 с**; 10-часовой 4K при 0.1× (150 с) в него
    не влезает и уходит в `deferred` — так и решено. Если «живой, но без кадров» случай не встречается, проверку
    движения можно не вводить;
  - **хеширование кадров** после ffmpeg — heartbeat на кадр, порог живости тот же;
  - **общий** 15-минутный лимит для медиа **убрать**;
  - **память** — как есть (плюс D5 для Windows).
- Часы — **без сна**: Windows `QueryUnbiasedInterruptTime`, POSIX `mach_absolute_time`/`CLOCK_MONOTONIC` (иначе сон
  ноутбука «убивает» здоровое видео). Windows API проверен: 2.01 с против 2.00 с у секундомера.
- Сигналы: звук — каждый прочитанный кусок stdout; видео — строки `-progress pipe:1` (`out_time_us`, `frame`);
  документы/PDF — шаг уже отдельный `prepare`; картинки — файл в батче.
- Сообщения остановки: «gave no sign for N s» / «made no progress for N s» / «frozen at 00:12:30 for N minutes».

### D2. Нагрузка длинных чтений — только когда человек работает

Целевое распределение: телефонные клипы (минуты), скринкасты, фильмы 1–3 ч, фото и документы. Десятичасовой 4K на
слабой машине — хвост, под который не оптимизируем: такой файл дешевле остановить и отложить (D3), чем закладывать
под него бюджеты и тормозить всех.

- **В простое** (нет ввода N минут — тот же `Idle`, что у `--rest-when-idle`) медиа читается **на полной скорости и
  обычном приоритете**: замер на простаивающей машине показал Idle = Normal (14.3 против 14.2 с, блоки те же), то есть
  на свободной машине троттлинг ничего не даёт и не нужен.
- **Пока человек работает** — дочерние ffmpeg в BELOW_NORMAL/IDLE (Windows `SetPriorityClass` ребёнку, POSIX
  `setpriority`; helper не трогаем — на POSIX `nice` не откатить), плюс `-threads 1 -filter_threads 1`. Замер: под 12
  занятыми ядрами Idle-декод 4K шёл 113 с против 13.4 с (в 8.4 раза медленнее), блоки в среднем через 3.3 с (§3.1).
- Решение принимается **при запуске каждого чтения** (`IndexOptions.userIsActive`): следующий файл выберет заново.
  Менять приоритет на ходу не стали — по замерам выигрыш не стоит отдельного пути, а `nice` на POSIX всё равно не
  поднимается.
- **Файлы, которые sync только что поставил в очередь, читаются на полной скорости**, даже когда человек за
  компьютером: первый запуск и добавленная папка — это «я жду этих результатов», а не «уступи мне». Уступает только
  старый backlog (`Indexer.Job.queuedNow`). Замер: 4K-клип 90 с из свежей папки — **12.1 с**, тот же файл из старого
  backlog — **29.7 с**; 1080p 60 с: **1.0 с** против **4.3 с** на одном потоке.
- Idle-only для медиа **не делать**: при активной работе медиа всё равно индексируется, просто медленнее.
- **Index Now** (трей, меню окна, Settings → Folders) снимает торможение на этот запуск: helper получает `speed full`,
  следующее чтение медиа идёт на всех потоках, гейт простоя для длинных файлов снят, на Windows helper поднимается в
  NORMAL (оболочка стартует его BELOW_NORMAL). Режим живёт до конца этого helper'а, следующий — снова автоматический.
  Снимаются и Pause, и окно часов (человек попросил явно): `held_now` не останавливает такой запуск, а после его конца
  расписание и Pause снова в силе.
- Опция (не в первой версии): «видео/аудио: сразу / после коротких / только в простое».

### D3. Очередь и остановки

- Состояние **`deferred`** (TEXT, схема не меняется): остановленный файл попадает туда с временем «попробовать после»
  в `info.retry_after` (backoff: 1 ч, затем 1 день), сортируется **после всех**, берётся, когда основное пусто;
  `failed` остаётся для явных ошибок чтения (не остановок). Длинный файл, который уже читался, по-прежнему становится
  `done` с тем, что успели прочитать.
- Оболочка: выход 75 перезапускает **всегда**, если у выхода есть заметка (её путь пишется в `stopped-file.json`) — это
  и есть прогресс. Нынешнее «3 за 10 минут» — **эвристика из кода, без данных**; её задача — не дать зациклиться.
  Замена:
  - заметка есть → перезапуск сразу (серия из 100 плохих файлов = 100 быстрых перезапусков, все помечены);
  - тот же путь остановлен **дважды подряд** → не перезапускать снова (файл уже `deferred`, следующий sync разберётся);
  - выход **без заметки** (краш) → backoff 2 с, 10 с, 60 с и затем «индексирование остановлено»; окно времени не нужно,
    счётчик подряд идущих крахов достаточно. Счётчик сбрасывается чистым выходом или остановкой на файле.
- Старые `failed` получают **один бесплатный повтор** при первом запуске этой версии (`readAgainOnce`, meta
  `stopped_retried`): без него строки, помеченные прошлыми версиями, остались бы навсегда.
- Ручного действия «Попробовать отложенные/неудачные ещё раз» в этой итерации нет: остановленное возвращается само по
  backoff, а старые `failed` — однократным повтором выше. Перезапуск после остановки — с обычным приоритетом: замеров
  «низкий приоритет помогает» нет, а helper и так даёт дорогу (D2).

### D4. «Сильная полоса» для медиа — закрыто спайком

- **4a уже есть:** `fill` держит не-картинки на глубине 1, то есть следующее задание готовится, пока встраивается
  текущее; картинки — на `prepareAhead` (число воркеров).
- **Спайк:** видео 180 с (4K) читалось **20 с**; 200 заметок, добавленных на 3.2 с и отправленных новым `sync`, начали
  индексироваться только на **20.2 с** — ждут конца текущего файла. Это не лечится read-ahead: файлы приходят новым
  sync уже после старта видео, а `shouldStop` проверяется только между заданиями.
- **4b в описанном виде не помогает:** «одно медиа готовится в фоне, основной поток читает короткие» касается одной
  очереди, а тут нужен новый sync. Вытеснение чтения без чанкования хуже ожидания: файл пришлось бы перечитывать
  целиком (для фильма — снова 10+ минут). Чанкование видео/аудио (шаги, как у PDF) — отдельное большое решение, в план
  не входит.
- Итог: оставлено как есть. Короткие файлы, пришедшие во время видео, ждут конца этого файла; медиа и так идёт
  последним, а свежие файлы больше не уступают по скорости (D2).

### D5. Windows: память

- `Watchdog.footprint()` для Windows через `K32GetProcessMemoryInfo` (`WorkingSetSize` или `PrivateUsage`), те же
  4–8 ГБ. API проверен: `WorkingSetSize` совпал с `Get-Process` (70 МБ). Пик на TIFF 64 МП — 378 МБ у ffmpeg и 183 МБ
  RGB, то есть 45 МП NEF далеко от 8 ГБ: на Windows лимит нужен для убежавших документов, а не для фото (#182 — про
  Apple RAW-декодер).
- Это превращает OOM-крах без заметки в обычную остановку с заметкой.
- Падения без заметки (AV) остаются неатрибутированными; «хлебная крошка» `reading.json` — отдельным решением позже,
  если после D5 такие падения останутся.

## 3. Проверки до кода (спайки, без изменений продукта)

### 3.1. Проведено (2026-11-25, эта машина, вендоренный ffmpeg 8.1)

**Прогресс и движение (спайки 1–2):**

- Блоки `-progress`: **каждые ~0.5 с** (0.5–0.6), стабильно; при `-readrate 0.2` тоже.
- `out_time` двигается по кадрам: шаг 3 с при 0.2× → **каждые 15 с** (замер: 7.4 s → 22.0 → 37.2 → 52.3…).
- 4K-клип 60 с, `-threads 1`, полная скорость: **14.3 с** (≈4.2× реального времени), блоков 27, `out_time`
  менялся 20 раз (≈0.7 с).
- Отсюда: 20 с живости = 0.5 с × 40 — подтверждено; порог движения 90–120 с покрывает 1–3 ч при 0.1× (шаг 3–9 с →
  30–90 с между кадрами), а 10-часовой 4K при 0.1× (шаг 30 с → 150 с) в него не влезает и уходит в `deferred` — как и
  решено.

**Приоритет под нагрузкой (спайк 1, продолжение):** 12 занятых ядер (12 процессов-нагрузчиков), тот же 4K-клип,
`-threads 1`: Normal — **13.4 с**, Idle — **113.1 с** (в 8.4 раза медленнее), блоков 34 за 113 с (в среднем **3.3 с**
вместо 0.5). Значит на низком приоритете порог живости нужно поднимать: **40 с** обоснован, 20 с — нет. Точный
максимальный разрыв в этом прогоне не снят (повторный замер с таймстампами не воспроизвёл нагрузку), но среднее
растяжение подтверждает направление.

**SMB (спайк 3, продолжение):** локальная шара `\\localhost\D$` — `ffprobe` **64–75 мс**, как локально. Реальная
сеть не измерена; для неё порог остаётся отдельным.

**Внешний USB HDD (спайк 3, часть):** Seagate Backup Plus на `L:` (NTFS, USB): запись 46 МБ/с; `ffprobe` **61–75 мс**,
первый блок **0.58 с**, декод 4K-30 с — **7.4 с** против 7.3 с локально. Диск был раскручен, поэтому это не тест
спящего диска; раскрутка по паспорту 5–15 с укладывается в 30-секундный старт (оценка, не замер).

**TIFF/память (спайк 4, часть):** TIFF 8000×8000 (64 МП): пик ffmpeg **378 МБ**, RGB-кадр 183 МБ. Для 45 МП NEF это
~135 МБ RGB и сотни мегабайт декодера — **до 8 ГБ на Windows не дотягивает**; лимит памяти на Windows нужен для
убежавших документов, а не для фото. Случай #182 (8 ГБ на NEF) — это Apple RAW-декодер, не наш Windows-путь.

**Остановки (спайк 5, часть):** живой `index-service` с открытым stdin: run1 — заметка с путём и причиной, выход **75**;
run2 — при старте берёт заметку, событие `stopped`, выход **0**, файл больше не читается. Если заметку потерять
(стенд удалял её), тот же файл останавливается снова — ровно тот случай, ради которого нужен guard «тот же путь дважды».
Оболочка (3/10) проверяется только в приложении.

**Старт и `ffprobe` (спайк 3, часть):** локально 47–68 мс на файлах 0.8 МБ и 212 МБ (HDD D: и NVMe C: — разницы нет).
То есть запуск и зонд локально — доли секунды; 30-секундный порог «старт» более чем достаточен. **SMB и «спящий» HDD
не измерены** — нет шары/диска; для них остаётся правило `max(60 с, 2×)` или отдельный порог по сетевому пути.

**Windows API (спайки 4–5, часть):** `QueryUnbiasedInterruptTime` работает (2.01 с против 2.00 с у секундомера);
`GetProcessMemoryInfo` возвращает тот же WorkingSet, что `Get-Process` (70 МБ). Оба пригодны; NEF/TIFF и пик памяти
helper'а не измерены — нет файла.

**Остановки (спайк 7, часть):** запуск `index-service` вне приложения оказался не conclusively: сервис синхронизирует
и выходит, не индексируя (в приложении команды `--backfill`/`new-limit` приходят иначе). Семантика `markStopped`
подтверждена по коду; живой тест «4 плохих файла + краш без заметки» остаётся за гейтом в приложении.

**Не измерено:** конкуренция приоритетов, SMB/спящий HDD, NEF/TIFF, прототип полосы 4a/4b.

### 3.2. Что осталось и как это не блокирует старт

1. **Реальная SMB-шара** — сейчас недоступна. Сетевой стартовый бюджет остаётся **политикой, а не замером**: для UNC
   путей 90 с (типичные таймауты SMB 30–60 с), уточнить, когда появится шара. Локальные и внешние USB — измерены
   (30 с с запасом). TV-box с ADB для этого не подходит: ADB не даёт UNC-путь, движок индексирует файловые пути, и
   такой тест измерил бы копирование по ADB, а не SMB-задержки; нужен SMB-сервер на боксе или любая шара в сети.
2. **Спящий внешний HDD** — попытка сделана 2026-11-25: таймаут диска Windows выставлен в 60 с, `L:` не трогали
   200 с, чтение 64 КБ с `FILE_FLAG_NO_BUFFERING` (мимо кэша) — **1 мс**. То есть этот USB-диск не паркуется таймаутом
   ОС (или мост игнорирует standby); «спящий» случай остаётся неизмеренным. Нужен диск, который точно спит, и
   `smartctl -n standby` для подтверждения; бюджет 30 с пока опирается на паспортные 5–15 с раскрутки.
3. **D4** — закрыто спайком: 4a уже есть, 4b без чанкования не помогает (см. §2 D4).
4. **Политика перезапусков оболочки** (3/10, краш без заметки) — проверяется только в приложении, гейтом.

Ни один из этих пунктов не меняет уже измеренные пороги (живость 20/40 с, движение 90–120 с, старт 30 с локально);
D1–D5 сделаны (D4 закрыт спайком), 0.1.24 выпущен 2026-11-25 (`v0.1.24`); сетевой порог уточним по мере появления
условий.

### 3.3. Сделано: D1–D5, Index Now и пакет 0.1.24 (2026-11-25)

- **D1.** `WatchdogPolicy` (`Sources/DigUpKit/WatchdogPolicy.swift`): старт 30 с, живость 20 с (40 с у чтения на низком
  приоритете, см. D2), движение 120 с — только для медиа; для остальных прежний общий лимит 15 минут (`--time-limit`).
  Часы — `Monotonic` без сна (Windows `QueryUnbiasedInterruptTime`, POSIX `CLOCK_MONOTONIC`). `Indexer` держит каждое
  чтение токеном (`started`, `lastSignal`, `lastMove`, `hasSignal`) и отдаёт наблюдателю **чтение с самым долгим
  молчанием**, а не самое старое. Сигналы: блоки `-progress` (живость) и `out_time_us` (движение) в видео, кусок звука
  в аудио, кадр при хешировании; Apple-ветка шлёт сигнал на каждый буфер/кадр.
- **D2.** `IndexOptions.userIsActive` (замыкание; в helper'е — `RestPacing.atTheMachine` по тому же `--rest-when-idle`,
  что и отдых длинных файлов, 0 у скрипта). Решение — **на каждое чтение**: `FFmpeg.run(lowPriority:)` ставит ребёнку
  BELOW_NORMAL (Windows `SetPriorityClass`) или nice 10 (POSIX `setpriority`) и добавляет `-threads 1
  -filter_threads 1`. Оболочка и так стартует helper в BELOW_NORMAL (`Launch.background`), так что в приложении
  реально меняются потоки, а приоритет ребёнка совпадает с родительским. `--rest-when-idle` в простое = полная
  скорость. Index Now поднимает helper в NORMAL и снимает ограничение (см. ниже). На Apple флаг принимается, но декод
  идёт в этом процессе — там ничего не меняется.
- **D3.** `IndexStore.markStopped` пишет `state='deferred'` и `info.retry_after` (1 ч; ещё одна остановка — 1 день);
  `pending()`/`pendingCount()` берут просроченные `deferred` **после** обычных `pending`, а не просроченные не берут
  вовсе. `readAgainOnce` один раз (meta `stopped_retried`) возвращает в очередь строки, которые прошлые версии оставили
  `failed`. В `SearchService` появился счётчик `deferred`, в Settings — строка «N will be tried again». Оболочка:
  выход 75 с заметкой перезапускает helper, тот же путь дважды подряд — нет; выход без заметки — backoff 2/10/60 с,
  затем «Indexing stopped: the helper keeps failing»; эвристика «3 за 10 минут» удалена.
- **D4.** Спайк «180-секундное 4K-видео + 200 заметок на 3-й секунде»: видео читалось 20 с, заметки начали
  индексироваться на 20.2 с — ждут конца файла. 4a (следующее задание готовится, пока встраивается текущее) уже был;
  4b в описанном виде не помогает, потому что файлы приходят новым sync. Решение по D4 — оставить как есть (см. §2 D4).
- **D5.** `Watchdog.footprint()` на Windows — `K32GetProcessMemoryInfo`/`WorkingSetSize` (то же число, что в Task
  Manager). Лимит памяти считается от физической памяти, как раньше (4–8 ГБ).
- **Index Now.** Раньше трей и меню окна только просили sync (и были выключены, пока идёт индексация, стоит Pause или
  часы). Теперь `index_now` (трей, меню окна, кнопка в Settings → Folders перед Pause) стартует или будит helper и шлёт
  ему `speed full` (в CLI — `--full-speed`): `ManualIndexing` снимает D2-торможение, гейт простоя и, на Windows,
  поднимает helper в NORMAL. Снимаются Pause **и окно часов** — осознанный запрос важнее расписания; `held_now` не
  останавливает такой запуск, а после его конца расписание и Pause снова в силе. Режим держится до конца этого
  helper'а; следующий — автоматический. Включение «Index Now» больше не зависит от `Status.busy` — оно нужно как раз во
  время индексации, паузы и часов.
- **Живые проверки** (Debug-helper, `index-service` с открытым stdin):
  - 10-минутное видео с `--time-limit 1` — **доиндексировано за 52 с, выход 0**, заметки нет: общий лимит медиа больше
    не применяется (старый остановил бы его на первой секунде);
  - `pose.pdf` (15 страниц) с `--time-limit 1` — **выход 75**, заметка `{"path": …/pose.pdf, "why": "took more than
    1 seconds to read"}`: для документов лимит остался;
  - `--memory-limit 600` — **выход 75**, заметка «needed more than 600 MB of memory»; тот же набор с
    `--memory-limit 2000` — **выход 0**, оба файла проиндексированы. Если лимит ниже собственного старта helper'а,
    в заметке нет пути (`no file being read`) — оболочка примет это за краш и не зациклится; 4–8 ГБ далеко выше;
  - **D2, 4K-клип 90 с**: с принудительным «человек за компьютером» (`--rest-when-idle 100000`) опрос каждые 200 мс
    видел только **BelowNormal + `-threads 1`**, индексация **28.7 с**; без гейта (`--rest-when-idle` нет) —
    **Normal + потоки по умолчанию**, **11.6 с**. Оба прогона — выход 0, 16 кадров. То есть под человеком 4K идёт в
    2.5 раза медленнее, в простое — на полной скорости, как решено;
  - **D3, тот же PDF**: первый запуск — выход 75 и заметка; второй — `stopped`, файл **не читается**, выход 0, в
    индексе `deferred` с `retry_after` ≈ +1 ч. Срок сдвинут на «сейчас» (SQLite), добавлен `note.txt` — третий запуск
    читает **сначала документ, потом остановленный файл**, снова выход 75 с заметкой; четвёртый — `stopped`, и вторая
    остановка даёт `retry_after` ≈ **+24 ч**. То есть очередь, срок и «после всех» работают;
  - **Index Now, 4K-клип 90 с** (`--rest-when-idle 100000`): автоматически — ffmpeg **BELOW_NORMAL + `-threads 1`**,
    чтение **28.5 с**; с `--full-speed` — **NORMAL, потоки по умолчанию**, ~13 с (wall 73 с минус 60 с linger); с
    `speed full` в stdin — то же. В прогоне с вручную понижённым классом helper'а после `speed full` он стал
    Normal, а уже запущенный ffmpeg доработал как был: режим действует **со следующего чтения**;
  - **Свежая папка против backlog, 4K-клип 90 с** (`--rest-when-idle 100000`): файл, который sync только что
    поставил в очередь, — **12.1 с** (NORMAL, потоки по умолчанию); тот же файл, оставшийся pending от прошлого
    запуска (helper убит после sync), — **29.7 с** (BELOW_NORMAL, `-threads 1`). 1080p 60 с без нагрузки: **1.0 с**
    против **4.3 с** на одном потоке — торможение заметно и на телефонном разрешении;
  - **Гейт простоя, PDF на 80 страниц** (`--rest-when-idle 100000`): автоматически после первых 30 страниц —
    `rest waiting`, 50 страниц ждут простоя; с `--full-speed` — страницы 31–60, затем 61–80, `summary rest`, done за
    2.6 с. То есть Index Now снимает и этот гейт;
  - Юнит-тесты: политика (6) — общий лимит у документов, старт медиа, сброс молчания сигналом, отдельное движение,
    40 с у низкого приоритета, 3-часовой фильм с прогрессом не останавливается; `RestPacing` — «человек за
    компьютером» и отключённый гейт; `IndexStore` — `deferred` и срок 1 ч → 1 день, просроченный файл идёт последним,
    старый `failed` получает один повтор.
- **Осталось от D3:** политика оболочки (тот же путь дважды, backoff на крашах) юнит-тестами не покрыта — она живёт в
  `index_ended` и проверяется только запуском приложения; ручного «Попробовать ещё раз» нет, как записано в D3.
- **Осталось от D1:** позиция в сообщении о движении («frozen at 00:12:30») не сделана: наблюдатель знает время, но не
  `out_time`; без этого сообщение остаётся «stopped moving for N minutes».

## 4. Последствия (что затронет)

- **Свежесть медиа**: D2/D4 делают медиа позже только при активной работе; в простое — полная скорость. Index Now
  (трей, меню окна, Settings) снимает торможение на этот запуск, поэтому опция «только в простое» не нужна; отдельной
  строки статуса «идёт на полной скорости» пока нет.
- **Производительность**: в простое не платим ничем; торможение — только пока человек работает. Хвост (10-часовой 4K)
  не диктует бюджеты: он останавливается и уходит в `deferred`, а не заставляет всех ждать дольше.
- **Состояния/интерфейс**: `deferred` — новый счётчик и строка статуса; окно и `IndexService` знают только
  `pending/done/partial/skipped/failed` — провести через все места.
- **Перезапуски**: 75 всегда → много перезапусков на серии плохих файлов (каждый помечает один); guard только для
  падений без заметки, иначе цикл.
- **Память**: D4b — два медиа в работе; кадры на диске, модель грузит один батч; проверить `frameBudget`.
- **Платформы**: D5 и D2 — разные API на Windows/POSIX; POSIX `nice` не откатывается, поэтому только дети.
- **Схема**: `deferred` — значение в TEXT-поле, миграции нет; но старые индексы должны корректно показывать новое
  состояние (проверить чтение/запись и окно).
- **Тесты**: юнит на бюджеты/часы (подставные часы и сигналы); интеграция `--time-limit`/`--memory-limit` на маленьком
  фикстуре; живой гейт: папка с медленным видео и пачкой коротких файлов, проверка «короткие не ждут» (если 4b),
  статусов, отсутствия temp; существующие гейты (индекс/поиск) не должны измениться.
- **Документация**: `AGENTS.md`/`docs/development-guide.md` — новое поведение; `--time-limit` help; заметка о
  `deferred` для окна.

## 5. Порядок работ

1. Спайки 1–7, цифры в план (ничего не меняем в продукте).
2. Уточнение плана: бюджеты, нужна ли 4b, как показывать `deferred`.
3. D1 (прогресс, фазы, часы) + тесты. — **сделано**
4. D5 (память Windows) + тест. — **сделано**
5. D2 (приоритет детей, `-threads 1`) + замеры. — **сделано**
6. D3 (`deferred`, перезапуски, retry) + тесты. — **сделано**
7. D4a, затем 4b только по результату спайка. — **закрыто** (4a уже есть; 4b без чанкования не помогает)
8. Пакет, полный набор гейтов, запись в guide. — **выпущен 0.1.24** (`v0.1.24`, 2026-11-25): живой прогон пакетной
   пары — Index Now на паузе и вне часов стартует, helper Normal, ffmpeg на всех потоках, после `idle` расписание
   возвращается; первый файл проиндексирован. Zip 481 477 302 байта, SHA-256 `1362507a...`.

Каждый шаг — отдельный коммит; релиз не публикуется, пока не проверено на пакетной паре.

## 6. Чего в этом плане нет

- «Хлебной крошки» для падений без заметки (отдельное решение, риск обвинить не тот файл).
- Idle-only для медиа (отвергнуто: на активной машине медиа не индексировалось бы вовсе).
- Настройки лимитов в интерфейсе (пока только CLI/внутренние значения).
- Изменений в поиске, OCR, схеме индекса, кроме значения `deferred`.
