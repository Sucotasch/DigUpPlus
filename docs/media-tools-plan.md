# Медиа-инструменты: видео-хувер, кадры, правка изображений

**Статус:** план 2026-11-24. Порядок работ: **видео-хувер** → **последовательность кадров и сетка** → **правка
изображений**. Ниже — предварительные решения (не предположения: где факт не проверен, это сказано явно), последствия
для остального приложения и список спайков, которые надо провести до кода.

## 0. Что уже есть

- Правая панель главного окна: у видео кадр + ▶, `Save frame` до и после проигрывания (0.1.21).
- Меню видео-результата: `Save Frame at …` (момент совпадения) и `Copy Frame` (PNG в буфер) — 0.1.20.
- Space в главном окне: большой просмотр, видео играет с момента, `Save frame` берёт текущий кадр.
- Панель по хоткею (`index.html` + `panel.js`): быстрый поиск «поверх» других программ, свой маленький список и свой
  Space-просмотр. **Инструменты туда не добавляем** (транзитная, клавиатурная поверхность).
- Панель по хоткею: **визуальный баг углов исправлен** — причина и проверка в §5.

## 1. Видео-хувер (следующее)

Всплывающий под курсором плеер в главном окне результатов — то, что в Imagus-Mass-Download-Mod сделано для видео.

Проверено по коду (2026-11-24), до реализации:

- **Ховер есть только у карточек сетки**: `peekOnHover` зовётся из `cell()`; `tableRow()` ховера не имеет, а строка во всю
  ширину — «сбоку от строки» места нет. **Решение: в таблице плеера нет** (там клик и Space, как сейчас); панель по
  хоткею и боковая панель — тоже нет (в боковой уже есть плеер).
- Ховер картинок: 300 мс на `pointermove`, закрытие на `pointerleave`. Плеер — тот же ритм, но с паузой 250 мс, чтобы
  успеть перейти зазор 12 px до кнопок.
- Прямоугольник карточки (`getBoundingClientRect`) даёт позицию. Область результатов — `#content`
  (`overflow-y: auto`), справа `#side` 324 px, снизу `#batch`. **Решение: границы — прямоугольник `#content`, не окна**;
  иначе закреплённый плеер накрыл бы боковую панель и панель операций.
- `renderOf(video)` = `["video", hit.loc ?? 0.5]`; `loc` есть только у хита-кадра (сегмент), у найденного по имени его
  нет. `render` умеет отдавать кадр видео как data-URL — fallback не требует нового op'а.
- Видео уже играется в боковой панели и большом просмотре по `fileURL(path)#t=<loc>` (0.1.20–0.1.21, живой тест): asset
  protocol отдаёт видео и старт с момента работает. Muted-автозапуск Chromium разрешает — проверить гейтом.
- Свои клавиши окна перехватывают `Tab` (поле ↔ результаты, `preventDefault`) и `Space` (большой просмотр). **Решение:
  клавиши плеера — только когда фокус внутри него (клик по плееру); Tab до него не доходит, клавиатурный просмотр
  остаётся Space/большим просмотром. Ховер фокус не забирает.**
- Файловые операции идут одной точкой — `operate()` → `file_operation` (Move/Copy/Delete). Пока плеер играет, файл
  открыт декодером WebView2: move/delete того же файла упрётся в sharing violation. **Решение: `operate()` закрывает
  плеер перед вызовом.**
- Правый клик: документный `contextmenu` (capture) прячет peek и открывает меню файла. **Решение: по плееру меню нет
  (долгое нажатие = pin), вне плеера — меню как обычно, плеер закрывается.**
- Ничего в UI сегодня не уважает `prefers-reduced-motion`. **Решение: при reduce автозапуска нет** — кадр helper'а и
  Play.
- В вебвью уже есть localStorage (`frameFolder`). **Решение: `hoverVolume` там же**, не в Settings: это свойство окна.
- `renderContent()` пересобирает карточки: **незакреплённый плеер закрывается, закреплённый живёт** (у него нет привязки
  к карточке). Скролл списка — так же; колесо над плеером список не листает.
- Формат, который WebView2 не играет, в репозитории не представлен. **Решение: фикстур `broken.mp4` = MPEG-4 Part 2**
  (WebView2 не декодирует, ffmpeg helper'а отдаёт кадр) — им проверяется fallback в гейте.

Решения:

| Что | Решение |
|---|---|
| Где | Сетка главного окна. В таблице нет (строке негде встать сбоку); панель по хоткею и боковая панель — нет |
| Триггер | 300 мс на карточке; закрытие через 250 мс после ухода с карточки и с плеера |
| Позиция | Справа (12 px), иначе слева, иначе снизу, иначе сверху; внутри `#content`; карточку не накрывает, пока есть куда |
| Размер | 480×270 — рамка плеера; видео вписано `object-fit: contain` (поля), контролы одной ширины |
| Старт | `max(0, loc − 2)`; у name-хита (нет `loc`) — с 0 |
| Звук | Всегда muted при открытии; громкость из `hoverVolume` (25 % по умолчанию); звук — только действием пользователя |
| Зацикливание | Только если длительность < 60 с |
| Один плеер | Один `<video>` на окно; при открытии — `pause` всем остальным видео страницы; при закрытии — `pause`, снять `src` |
| Управление | Играть/пауза, время, seek (range), громкость (range), Mute, Pin, Save frame, × |
| Указатель | Окно интерактивно; уход в него не закрывает, уход из него закрывает, если не закреплено |
| Закрепление | Долгий правый клик (≥ 450 мс) по уже показанному плееру или Pin; таскается за шапку; закреплено одно; раннее отпускание отменяет |
| Клавиши | Только при фокусе в плеере (клик): Space, ←/→ ±5 с (Shift 15), ↑/↓ громкость, M, Esc; Tab до плеера не доходит |
| Reduce motion | Автозапуска нет: кадр helper'а и Play |
| Неиграемый кодек | Кадр helper'а + строка «Windows не проигрывает этот формат» + `Open`; `Save frame` в шапке; повторно не пробуем |
| Контекстное меню | По карточке — меню файла (плеер закрывается); по плееру — меню нет (долгое нажатие = pin) |
| Файловые операции | Перед Move/Copy/Delete плеер закрывается: файл открыт декодером |
| Что не делаем | Скорости 0.5–2×, HLS/DASH, полный экран, второй плеер, ховер в таблице/панели |

Последствия и гейты:

- **Autoplay и звук**: muted-автозапуск разрешён; первый звук — жест (кнопка Mute/ползунок/M). Гейт: после открытия
  `video.muted === true`, `volume === 0.25`.
- **Кодеки**: MP4/H.264 и WebM играют, MKV/HEVC/TS — как повезёт. Гейт: `big.mp4` и `shots.ts` играют; `broken.mp4`
  (MPEG-4 Part 2) даёт fallback с кадром helper'а и не повторяет попытку в этой сессии.
- **Один декодер**: плеер создаётся только для наведённого; уход — `pause` + `delete src`; большой просмотр (Space)
  закрывает плеер; перестройка результатов и скролл — тоже (кроме закреплённого).
- **Файл занят**: пока плеер держит видео, move/delete того же файла невозможны — `operate()` закрывает плеер; рендер
  кадра helper'ом (Save frame) читает параллельно и не мешает.
- **Производительность**: `preload=metadata`, никакой предзагрузки; один файл за раз; 300 мс отсекают проносы по сетке.
  Гейт: время до первого кадра на 4K-файле и отсутствие чтения всех видео подряд.
- **Конфликты**: перетаскивание выделения (buttons) закрывает; клик по чекбоксу — нет; контекстное меню карточки
  закрывает; боковая панель и большой просмотр останавливаются, не закрываются.
- **Доступность**: `role="dialog"`, у всех кнопок и ползунков `aria-label`, фокус не забирается, Esc по фокусу,
  reduce-motion без автозапуска.
- **Тесты**: живой CDP (появление/300 мс; muted и 25 %; старт `loc−2`; loop по длительности; позиция сбоку; позиция
  внутри `#content`; Space после клика; ↑/M; долгий правый клик закрепляет и переживает уход; Pin снимает; × закрывает;
  громкость запоминается и остаётся muted; второй хувер заменяет; fallback `broken.mp4`; скриншот) + гейт после сборки.
  Пометка в `docs/development-guide.md`.

## 2. Последовательность кадров и сетка (после видео-хувера)

Два **отдельных** пункта меню видео-результата (как договорились): `Extract frames…` и `Contact sheet…`.

Предварительные решения:

| Что | Решение |
|---|---|
| Где | Меню видео-результата и кнопка `Frames…` в правой панели; не панель по хоткею |
| Старт | `hit.loc` (или текущий кадр боковой панели/большого просмотра, если открыт тот же файл) |
| Количество | 12 по умолчанию; максимум 120 |
| Шаг | «Каждые 1 с» по умолчанию; второй вариант — «равномерно по клипу» (N кадров на длительность) |
| Размер | Нативный по умолчанию; вариант 1280 px по длинной стороне |
| Выход последовательности | Папка `<видео> — frames` рядом с видео, файлы `0001.jpg…`; если папка есть — `— frames (2)`; ничего не перезаписывать |
| Сетка | Отдельный пункт; один JPEG `<видео> — sheet.jpg`; 4 колонки, до 24 кадров; без подписей времени в v1 (шрифт/лицензия не нужны) |
| Реализация | Один новый op helper'а `frames` (ffmpeg одним процессом: `-ss`, `fps`/`select`, `-frames:v`, для сетки `tile`), в отдельном потоке как `render`; ответ — папка/файл/число/ошибка |
| Ограничения | Нет отмены в v1 (один процесс; кнопка «Extracting…»); потолок N; предупредить об объёме (120×4K ≈ 1–2 ГБ) |
| Совместимость | Кадры извлекает ffmpeg — работает и там, где WebView2 не играет (MKV/HEVC/TS) |

Последствия:

- Новые файлы лежат внутри выбранного корня → обычный обход их проиндексирует (если правила папки включают картинки);
  индекс пишет не инструмент, а индексатор. Если папка исключена/`skipTypes` — копии не попадут в индекс, это выбор
  пользователя.
- Диск: последовательность — это N файлов; сетка — один. Потолки и предупреждение о размере обязательны.
- VFR-видео: `fps`-фильтр привязывает кадры к сетке времени; для «равномерно по клипу» шаг = duration/N. Проверить на
  реальном VFR-файле.
- `shots.ts` (3 цветных кадра по 4 с) — эталон для теста: 3 кадра, цвета R/G/B, времена внутри своих отрезков; сетка —
  один JPEG с 3 плитками. Живой тест: 2560×1440, 6 кадров, нативный размер, имена, отсутствие перезаписи.

## 3. Правка изображений (после кадров) — на месте, без копий

Решение (2026-11-24): правка **на месте**. Человек видит в результатах перевёрнутую картинку и поворачивает её; видит
PNG на 40 МБ и сжимает его в JPG. Копия `<имя> — edited` — это второй файл, лишнее место и мусор в выдаче; правка — такая
же операция над файлом, как Move/Delete, а не «Сохранить как». Опасность осознанная; ниже — то, что не даёт ей стать
потерей данных.

Смотрел `d:\...\Image Sorter\`: Tauri + JS (`cropperjs`) + Rust (`image`, `turbojpeg`, `png`, `kamadak-exif`).

Проверенные факты (по коду):

- **Поворот 90°** — уже in-place: `backup_file` копирует оригинал в temp, `rotate_image` пишет файл, шаг кладётся в
  undo-историю. Для JPEG lossless через libjpeg-turbo, если блоки MCU совпадают, иначе перекодирование. Undo/redo —
  `swap_edit`: байты бэкапа кладутся рядом с живым файлом и переименовываются на место (атомарно); обычная запись —
  `fs::write` прямо в файл, то есть сбой посреди неё оставит половину (у нас так нельзя).
- **Кроп** (Cropper.js, координаты в натуральных пикселях), **конвертация PNG→JPG** с качеством и **сохранением
  метаданных** (JPEG APPn/COM: EXIF/XMP/ICC/комментарии/AI-промпты; PNG tEXt/zTXt/iTXt; альфа заливается белым; если
  метаданные не влезают в JPEG — файл **не** пишется, чтобы не терять данные), просмотр/правка метаданных.
- **Конвертация заменяет файл**: пишет `<имя>.jpg` рядом, оригинал отправляет в **Корзину** (`trash`), имя при
  коллизии получает `(1)`.
- **Resize в Image Sorter нет** (в коде только поворот/кроп/конвертация) — его добавляем сами
  (`image::DynamicImage::resize`/`thumbnail`).
- **EXIF orientation Image Sorter не нормализует** (в коде её нет). Для нас это обязательно: DigUp показывает картинку
  повёрнутой по тегу (`RGBImage.oriented`), и после поворота пикселей тег надо сбросить в 1, иначе просмотрщик повернёт
  ещё раз.

Предварительные решения для DigUp:

| Что | Решение |
|---|---|
| Безопасность | **На месте**: оригинал меняется. Одна запись на одно действие, только через временный файл рядом и переименование на место (атомарно); при ошибке оригинал не тронут, temp удалён. Конвертация формата уносит оригинал в **Корзину** (восстановим), не удаляет. Отмена — стек 10 правок за сессию (бэкап в temp) |
| Где | Главное окно: меню результата, правая панель, большой просмотр. **Не** панель по хоткею, **не** хувер |
| Вход | `Rotate left` / `Rotate right` в меню и панели — сразу, без листа (частый случай: «перевёрнуто — повернул»). `Edit…` — лист с кропом/resize/форматом/качеством; поворот и флип в листе — превью, в запись идут одной операцией, то есть одно перекодирование |
| Инструменты v1 | Поворот 90° L/R, флип H/V, кроп (Cropper.js), resize по длинной стороне или %, выход JPEG (90 по умолчанию, 60–100) / PNG |
| Ориентация | Ориентацию EXIF печём в пиксели первой операцией, в выход пишем 0x0112 = 1 (у PNG тега нет) |
| Метаданные | Портированные `jpeg_meta`/`png_meta`/`exif_writer`: EXIF/XMP/ICC/COM и PNG-текст сохраняются; альфа на белом; AI-промпты из PNG в JPG — тем же способом (minify + Make/Model + COM); не влезло в JPEG — отказ с предложением PNG, файл не пишется |
| Форматы | Вход: JPEG/PNG/WebP/BMP/TIFF (что декодирует `image`); HEIC/RAW не правим (открываем в системе); анимации (GIF, animated WebP) — отказ, иначе потеряем кадры. Выход: JPEG/PNG |
| Конвертация | `<имя>.jpg` рядом, оригинал в Корзину, строку старого пути убираем сразу (`file_op delete`), новый JPG индексирует watcher. Если `<имя>.jpg` уже есть и это не тот же файл — отказ (никаких `(1)`: это была бы копия) |
| Undo | Стек 10 правок на сессию: temp-папка с бэкапами, чистится при выходе; `Ctrl+Z` в окне и кнопка в тосте («Rotated — Undo»). Redo нет |
| Реализация | Портируем Rust-модули Image Sorter в shell (`image_proc`, `jpeg_meta`, `png_meta`, `exif_writer`, `backup`; `metadata.rs` не нужен); зависимости `image` (default, без AVIF — без нативки), `png`, `kamadak-exif`. `cropper.min.js` (MIT) вендорим в `shell/ui/vendor` |
| Спайк до кода | (1) `image`+`png`+`kamadak-exif` собираются в shell на Windows и Linux — время и размер; (2) тесты Image Sorter проходят в нашей копии; (3) Cropper.js под нашей CSP (`img-src` знает `data:`) и в плоском UI: превью в лист идёт из `render` (data-URL, canvas не нужен), кроп считаем в долях превью и умножаем на натуральный размер; (4) настоящий PNG 40 МБ из ComfyUI → JPG: prompt/workflow уцелели; (5) фото с orientation 6: поворот даёт ровно один поворот; (6) `build-jpegtran.sh` даёт один exe без DLL, он поворачивает 4032×3024 без потерь (пиксели до/после идентичны) и честно отказывает `1366×768` |
| Если спайк провалится | Запасной путь — ffmpeg (поворот/кроп/resize/конвертация) **без метаданных**, с явным предупреждением в листе; решение по результату спайка, не заранее |

**Поворот без потерь (JPEG).** Математика тут не мешает: коэффициенты DCT можно транспонировать, не декодируя пиксели, —
поворот 90/180/270 и флипы выходят без потерь. Ориентация 6/8 печётся тем же поворотом (её угол суммируется с просьбой), тег
ставится в 1: «камера повернула» и «человек повернул» — один проход, одна запись. Ограничения: только эти углы (кроп и resize
без потерь невозможны), и transform «perfect» лишь когда обе стороны кратны MCU — 16 px при 4:2:0, 8 при 4:4:4: 4032×3024 и
6000×4000 проходят, 1366×768 нет. Для некратных `-perfect` отказывает, и тот же путь перекодирует в q95: молча срезать до
15 px нельзя. Инструмент — `jpegtran.exe` из libjpeg-turbo, статически собранный `scripts/build-jpegtran.sh` в
`Vendor/jpegtran/bin`, лежит в `helper\` рядом с ffmpeg/ffprobe/`ocr.exe`: тот же поиск «рядом с helper'ом», тот же `cp` в
`package-portable.sh` и SHA-256 в `vendor-checksums.json`. Rust-крейт `turbojpeg` отвергнут: он тянет CMake/NASM в сборку и
`turbojpeg.dll` в поставку ради одного вызова бинарника. Прогрессивные JPEG jpegtran тоже транскодирует без потерь (меняется
энтропийное кодирование, не пиксели); арифметическое кодирование, 12 бит и CMYK — отказ, перекодирование. PNG без потерь и так
(декод → пиксели → энкод), у него терять нечего. В тосте пишем, какой путь сработал: `Rotated — lossless` или
`Rotated — recoded`: человек иначе не узнает, потерял ли он качество, и начнёт бояться этой кнопки.

Почему не копия и не «Сохранить как»: копия удваивает место ровно там, где человек как раз пытается его сэкономить, и
добавляет в выдачу файл, который он не просил. Правка — это то же, что Move/Delete: одно осознанное действие над файлом.

Почему не через helper: helper намеренно read-only (MCP-сервер только читает и отдаёт окна текста), а правка — файловая
операция shell'а, как Move/Delete: диалоги, Корзина и retry уже там. Модель и индекс в записи не участвуют.

Последствия и проверки:

- **Индекс.** Тот же путь: watcher видит изменение (размер/mtime) примерно через 2 с и просит sync; строка уходит в
  pending, пересчитываются вектор, phash, OCR и текст. Пока индекс не догнал, поиск по новому виду картинку не находит —
  это секунды; на сетевом диске, где watcher не работает, до опроса (5 мин) или ручного Rescan. Пишем это в описании
  функции, чтобы «повернул, а поиск не видит» не выглядело багом. Если индексатор читал файл ровно в момент записи, он
  запишет старые размер/mtime — следующий sync увидит расхождение и прочитает файл ещё раз (самоисправление).
- **Свежесть в окне.** Сразу после записи страница перезапрашивает картинку с `?v=<mtime>` (спайк: принимает ли asset
  protocol query); если нет — правая панель и большой просмотр берут `render` (data-URL, уже есть), сетка обновится
  следующим поиском.
- **Одновременная индексация.** Индексатор может читать файл в этот момент: переименование на место упадёт с sharing
  violation — повторяем (retry, как в `file_ops`), поверх открытого файла не пишем. Читатель с открытым дескриптором
  дочитает старые байты: он увидит либо старый, либо новый файл, не половину.
- **Свободное место.** Temp-файл рядом требует размера результата поверх оригинала на том же диске; ошибка записи —
  оригинал цел, temp удалён.
- **Права.** Read-only, занятый файл, нет прав — текст ошибки, ничего не записано. Симлинк: сначала `canonicalize`,
  пишем в цель, ссылка остаётся ссылкой.
- **Корень.** Правим только файл, который показывает окно (вне корней тоже можно, как `save_frame`); в индекс инструмент
  не пишет.
- **Конвертация на Linux.** Корзина в shell — Windows (`SHFileOperationW`); на других системах v1 предлагает только
  правку в том же формате, а формат-конвертация говорит «не на этой системе». `trash`-крейт — отдельным шагом.
- **Доступность.** Лист: фокус-ловушка, Esc отменяет без записи, у кнопок `aria-label`, ошибки текстом (не только
  цветом), «Undo» в тосте фокусируемо.

Тесты:

- Портируемые юнит-тесты Image Sorter: поворот/кроп/метаданные/альфа/«не влезло — не пишем» + resize; orientation 6 →
  ровно один поворот и тег 1; PNG→JPG с prompt/workflow.
- Атомарность: сбой записи temp (read-only папка, переполнение) → оригинал побайтово тот же, temp не остался.
- Поворот JPEG: 4032×3024 через jpegtran → пиксели до/после идентичны, EXIF/ICC на месте, orientation = 1; 1366×768 →
  `-perfect` отказал, сработал q95-путь; orientation 6 + «поворот вправо» → ровно один поворот, не два.
- Undo: байты вернулись один в один; стек ограничен 10, старейший бэкап удалён.
- Индекс (живой): повернуть картинку из выдачи, дождаться sync, найти по новому виду (вектор обновился), phash другой;
  окно не показывает старый кадр.
- Конвертация (живой): PNG в Корзине, JPG на месте, строка переехала, поиск находит; `<имя>.jpg` уже есть → отказ.
- Живой UI (CDP): `Rotate right` из меню пишет файл; `Edit…` кроп → точный размер; Esc ничего не пишет.

## 4. Порядок, гейты, риски

1. **Видео-хувер** (0.1.22): UI + живой CDP-гейт; helper не меняется.
2. **Кадры + сетка**: новый op helper'а → полный zip; тест на `shots.ts` + живой; гейт.
3. **Правка изображений**: спайк зависимостей и `jpegtran` → перенос модулей + меню `Rotate`/лист + тесты; правка
   **на месте**.
   shell-only невозможен, если версия MCP меняется вместе с приложением (она вшита в helper) — каждый релиз сейчас
   полный zip; это отдельное наблюдение, не часть инструментов.

Риски:

- Видео-хувер: WebView2 не играет часть форматов (fallback обязателен); autoplay со звуком (muted по умолчанию
  снимает); конфликт долгого правого клика с меню строки (решено: только по окну); один декодер.
- Кадры: VFR/длинные 4K (время/диск); потолок N; сетка без подписей (иначе шрифт).
- Правка: на месте разрушительна — рельсы: одна атомарная запись, undo на 10, Корзина при конвертации, отказ на
  read-only/анимации/HEIC. Поворот JPEG без потерь есть, но не для всех размеров: некратные MCU (16 px при 4:2:0)
  перекодируются в q95, и это надо показывать (строка «recoded, not lossless» в тосте), а не выдавать за без потерь.
  Кроп/resize без потерь невозможны. Без нормализации EXIF orientation получим двойной поворот. Индекс догоняет через
  watcher (~2 с), на сетевых дисках — до 5 мин. Зависимости чистые Rust; `jpegtran.exe` — ещё один вендоренный бинарник
  в `helper\` (сборка + SHA-256 + `cp` в пакет), если `image` окажется тяжёлым для сборки — остаётся ffmpeg-путь без
  метаданных.

## 5. Панель по хоткею: баг углов (исправлено)

- **Причина (по пикселям скриншота):** углы панели скруглены (`.panel`, radius 18), но окно с `shadow(true)` рисует
  **прямоугольную серую рамку** по своим границам; между ней и скруглением видны «треугольники» — это фон/край окна, а
  не панель.
- **Фикс:** у окна панели `shadow(false)` — системная прямоугольная тень/рамка уходит, остаётся только скруглённая
  панель (фон окна прозрачный). **Проверено** снимком экрана: до — по границе окна шла серая линия 129, а в углу
  (24,24) был прямоугольный край; после — (24,24) чёрный (прозрачно), (24,40)/(40,24) 215 (собственная рамка панели),
  прямоугольника нет, только скругление.
- **Последствие:** у панели больше нет системной тени (на Windows она и была прямоугольной); при желании тень можно
  нарисовать CSS внутри окна с полями — отдельным решением, не сейчас.
- **Тест:** `.build/panel-shot.ps1` (запускает панель с `--debug-show` на scratch-настройках, снимает область окна) +
  `.build/panel-corners.png`, `.build/panel-tl.png`/`panel-tl-after.png`; повторять при изменениях окна панели.
