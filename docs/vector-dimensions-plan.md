# Размерность векторов: MRL 512d/256d — измерено на наших данных и отклонено

**Статус:** решение принято 2026-11-19, действует, пока не появится новое *размеченное* измерение (см. «Когда
возвращаться»). Размерность остаётся **768d**.
**Машина:** i7-5820K, RTX 4070 Ti SUPER 16 ГБ, Windows 10, CUDA 13.1, llama.cpp **b12540** (0.1.19),
модель `embeddinggemma-2-Q8_0` + `mmproj-embeddinggemma-2-Q8_0`, наши файлы.

## Задача

EmbeddingGemma 2 обучена с Matryoshka: карточка модели обещает «close to lossless down to 256 dimensions» и приводит
MTEB 61.36 → 60.41, MIEB (картинки) 65.67 → 64.16. Наш индекс держит 768d fp16 — 240 МБ на 156 тыс. векторов; 512d
дало бы 160 МБ, 256d — 80 МБ, и пропорционально меньше холодного чтения при старте. Стоит ли это делать?

**Правило продукта:** поиск по картинкам — главная особенность форка; потеря качества картинок ради ~100 МБ
недопустима. Поэтому обещания карточки проверялись не на её цифрах, а на нашем индексе и наших запросах.

## Как измерялось

- Векторы запросов — `digup worker --text-only` (тот же код, что у приложения) с нашим промптом
  `task: search result | query: …`; 12 запросов: английские и русские, про картинки, книги и аудио.
- Документы — 121 135 реальных векторов из копии индекса (`.build/real-index`): 4 061 картинка (у всех есть phash),
  460 документов, 1 200 аудиофайлов (читаются только по тегам, векторов нет).
- Для каждого d: ведущие d компонент **у документов и у запросов**, L2-нормировка (рецепт карточки), cosine, z по
  всем векторам, лучший сегмент на файл — то же ранжирование, что делает движок. Эталон — 768d.
- Отдельно для картинок: считается ли заменённая картинка **look-alike** заменённой (phash, порог 34.5 % — дефолт
  Find similar), и сколько из топа-10 768d осталось в топе-10.

## Результаты

### Картинки (4 061; главное)

| | 512d | 256d |
|---|---:|---:|
| Spearman по всему ранжированию, среднее / минимум | 0.957 / 0.916 | 0.867 / 0.794 |
| лидер 768d остаётся первым | 11/12 | 8/12 |
| лидер 768d остаётся в топ-5 | 12/12 | 11/12 |
| в топ-5 тот же файл или phash-look-alike (из 5) | **3.8** | 3.0 |
| из топа-10 768d осталось в топе-10 | **7.4/10** | 5.9/10 |

### Документы (460)

| | 512d | 256d |
|---|---:|---:|
| из топа-10 768d осталось в топе-10 | 8.1/10 | 6.1/10 |

То есть при 512d первая картинка почти всегда та же, но **~1.2 из топ-5 и ~2.6 из топ-10 — другие изображения**, и
phash подтверждает, что это не копии и не look-alike. При 256d — ~2 из 5 и ~4 из 10, лидер меняется в трети запросов.

### Слои Images ломают калибровку

Пороги visible/weak (0.648 / 0.600) — абсолютные косинусы; урезание их поднимает и сжимает распределение. Счётчики
по 4 061 картинке на запрос:

| запрос | 768d видимых/слабых | 512d | 256d |
|---|---:|---:|---:|
| «a dog on the beach» | 26 / 272 | 49 / 320 | 128 / 587 |
| «video thumbnail with a person» | 476 / 3 024 | 972 / 2 790 | 2 671 / 1 349 |

Даже если бы ранжирование осталось идеальным, фильтр показывал бы другие наборы: пороги пришлось бы перемерять под
каждую размерность.

## Решение и мотивы

**768d остаётся.** 512d экономит 80 МБ (240 → 160) и ~1.5× чтения векторов, но меняет ~1.2 из топ-5 и ~2.6 из топ-10
картинок на **другие** изображения, а слои Images требуют перекалибровки. По правилу «картинки — главное» это не
компенсация, а потеря; 100 МБ того не стоят. 256d отклонён тем более (лидер меняется в 4 запросах из 12).

Холодный старт, ради которого размерность и обсуждалась, уже закрыт иначе: 0.1.18 грузит модель и векторы в фоне,
окно отвечает словами и само повторяет запрос; 240 МБ читаются один раз и не блокируют поиск. Экономия 80 МБ дала бы
только меньше диска/чтения в фоне — не качество.

## Когда возвращаться

Только при **новых доказательствах**, а не при повторном чтении карточки модели:

1. Размеченный мини-eval по картинкам: 15–30 запросов, для каждого — картинка, которая обязана вернуться (не «похожая
   выдача», а конкретный файл); recall@5/@10 у 512d против 768d на **нашем** индексе.
2. Перезамер порогов слоёв visible/weak под выбранную размерность (абсолютные косинусы меняются).
3. Только **512d**; 256d — при отдельном доказательстве, что картинки не страдают (и с замером аудио: в этой выборке
   векторов аудио не было, по карточке 256d теряет на аудио ~4 %).
4. Любая смена размерности — это `vectorVersion`/fingerprint и полный реиндекс: считать это отдельным релизом.

## Чем воспроизвести

Скрипты и сырые результаты локальные (`.build` не коммитится):

```bash
python .build/mrl.py .build/real-index .build/mrl-report.json       # ранжирование 768/512/256 по группам
python .build/mrl-inspect.py .build/real-index .build/mrl-queries.json   # пути, Spearman
python .build/mrl-phash.py .build/real-index .build/mrl-queries.json     # look-alike в топ-5, recall@10
```

Нужны `DIGUP_MODELS=.dev/models` (скрипты выставляют сами) и собранный helper 0.1.19+; запросы —
`.build/mrl-queries.json`. Полный отчёт с цифрами: `.build/mrl-report.md`.
